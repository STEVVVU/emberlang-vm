# Ember Compiler and VM

Ember is a compact, statically typed compiler toolchain written in Rust. It
implements the work expected in a real compiler pipeline: source spans and
parser recovery, lexical name resolution, type checking, an inspectable
register IR, optimization passes, bytecode generation, diagnostics, and a
resource-limited VM.

The language is intentionally small. The project is about compiler engineering,
not unusual syntax or novelty features.

## Quick Start

Requires stable Rust (tested with Rust 1.96.0).

```sh
cargo build --release --bin ember
cargo run --bin ember -- check examples/fibonacci.em
cargo run --bin ember -- run examples/fibonacci.em
cargo run --bin ember -- disassemble examples/optimizer.em
```

Expected Fibonacci output:

```text
55
```

Install the CLI locally with `cargo install --path . --bin ember`.

## CLI

```text
ember check <file> [--no-opt]
ember run <file> [--no-opt] [--max-steps N] [--max-call-depth N] [--max-output-bytes N]
ember disassemble <file> [--no-opt]
```

- `check` runs lexing through type checking and reports optimization counters.
- `run` compiles and executes `main`, using its integer result as the exit code.
- `disassemble` prints deterministic register bytecode with resolved jumps.

Diagnostics use stable error codes, source locations, underlines, notes, and
actionable help:

```text
error[E4006]: initializer type does not match annotation: expected `int`, found `bool`
 --> tests/golden/type_error.em:2:5
  |
2 |     let attempts: int = true;
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^
 help: use an expression of type `int`
```

## Example

```text
fn sum(n: int) -> int {
    let total: int = 0;
    let index: int = 0;
    while index < n {
        total = total + index;
        index = index + 1;
    }
    return total;
}

fn main() -> int {
    print(sum(10));
    return 0;
}
```

See `examples/` for Fibonacci, nested control flow, and optimization-focused
programs.

## Compiler Pipeline

```text
source
  -> spanned tokens
  -> recovered AST
  -> name resolution
  -> static type checking
  -> register IR
  -> constant folding
  -> dead-result elimination
  -> bytecode
  -> sandboxed VM
```

The IR has explicit labels, branches, virtual registers, calls, and
source-bearing instructions. Constant folding is conservative at control-flow
boundaries. Dead-result elimination iterates to a fixed point and never removes
calls or output. See [`docs/architecture.md`](docs/architecture.md) for the
grammar, IR contract, pass invariants, bytecode model, and design tradeoffs.

### Why the parser is hand-written

The lexer and parser are hand-rolled recursive descent, not generated by
`lalrpop`, `chumsky`, `pest`, or a yacc derivative. That is a deliberate choice,
not an omission:

- **It is what production compilers do.** rustc, clang, GCC, Go, and TypeScript
  all hand-write their frontends. GCC migrated *away* from a Bison grammar to
  recursive descent; clang never used one.
- **Error recovery is the reason.** Most of this parser's complexity is producing
  a useful AST *after* a syntax error, with a span precise enough to underline and
  a message phrased for the user. Generated parsers optimize for accepting a valid
  grammar; recovery is where they fight you, and diagnostics are a headline
  feature here (see `src/diagnostic.rs`).
- **Precedence is not the hard part.** Expression precedence — the thing a grammar
  file genuinely makes tidier — is a small, well-understood slice of the frontend,
  handled here by precedence climbing.
- **The frontend is the point.** This is a portfolio compiler; delegating parsing
  to a library would remove the part that demonstrates the skill while adding a
  build-time codegen step and a generated-code debugging story.

The tradeoff is real and worth naming: a grammar file is a better *specification*
than a recursive-descent parser, and it makes ambiguity a build error rather than a
subtle precedence bug. The grammar is therefore written out explicitly in
[`docs/architecture.md`](docs/architecture.md) and kept in sync by the parser
tests. A larger language, or one whose syntax changed often, would tip this the
other way. Libraries *are* used where they are the industry answer and not the
exercise: `ariadne` renders diagnostics, `clap` parses argv, `criterion` and
`insta` handle benchmarking and snapshots, `rustc-hash` backs the internal tables.

## Safety and Determinism

The VM exposes no host filesystem, network, environment, or FFI operations.
Checked `i64` arithmetic traps on overflow and division by zero. Defaults bound
execution to 1,000,000 instructions, 256 call frames, 1 MB output, 65,536
registers per frame, and 10,000 functions. Compilation also caps source size and
token count.

Function/register allocation, optimization order, bytecode, disassembly, and
output are deterministic for identical source and options. A test compiles and
disassembles the same source twice and compares exact output.

## Verification

```sh
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets
cargo build --release
cargo bench -- --test          # compile and run every benchmark once, untimed
```

The 41-test suite includes:

- lexer/parser recovery and precedence;
- resolver scope errors and typo suggestions;
- operator, call, condition, and return typing;
- constant folding and dead-result removal;
- optimized/unoptimized behavior equivalence;
- function calls, loops, arithmetic traps, and VM limits;
- deterministic disassembly;
- CLI integration, argument parsing, and limit resolution;
- 10 committed snapshots covering every reviewable artifact the compiler emits
  (rendered diagnostics, optimized and unoptimized IR, disassembly);
- explicit platform-independence assertions on rendered diagnostics, plus a
  regression test that colored rendering does not depend on an attached console.

Diagnostic snapshots are asserted in the ASCII-only, escape-free `Plain` style, so
a snapshot recorded on Windows matches one verified on Linux byte for byte; a
CRLF copy of the same source is asserted to render identically, so a checkout with
`core.autocrlf=true` does not change them. ANSI escapes are exercised but never
snapshotted, since they are terminal-dependent by nature.

CI runs formatting, strict Clippy, all tests, and release builds on Linux and
Windows, plus a release-mode benchmark smoke test and an untimed `--test` run of
both criterion suites.

## Measured Evidence

`cargo run --release --bin benchmark` generates a deterministic 8,441-byte,
81-function input. Figures below are from **32 consecutive runs** of the release
binary on one Windows x86_64 machine, reported as median with the full observed
min–max envelope:

| Metric | Median | Observed range |
| --- | ---: | ---: |
| Full compile, fastest of 200 iterations | 884 µs | 771 – 984 µs |
| Full compile median of 200 iterations | 1.258 ms | 1.056 – 1.473 ms |
| Full compile p95 | 2.524 ms | 1.656 – 20.267 ms |
| VM throughput (5,000,400 instructions) | 128.8 M instr/s | 19.8 – 153.0 M instr/s |
| Constants folded per compile | 402 | identical in all 32 runs |
| Dead instructions removed per compile | 722 | identical in all 32 runs |
| Resulting bytecode instructions | 336 | identical in all 32 runs |

The measurement box is a power-managed laptop with unpinned clocks, sampled at
~100% CPU during the run, so the timing rows are **envelopes rather than point
claims** — p95 spans 12.2x and VM throughput 7.7x. The three deterministic rows
are the ones to hold the compiler to: they are properties of the compiler rather
than of the clock, and they did not move at all.

These are single-machine engineering baselines, not universal claims; nothing here
was measured on Linux. The raw artifact, the pooling method, and the reason both
benchmark harnesses exist are in [`benchmarks/`](benchmarks/).

## Limitations

Ember has no modules, strings, heap objects, closures, generics, or native
interop. The IR is not SSA; constant propagation is intrablock, and dead-code
elimination removes unused pure results but not unreachable blocks. Bytecode is
generated and executed in memory rather than loaded from untrusted files.

Those choices keep semantics and resource accounting reviewable. The natural
next compiler work would be CFG construction, dominators/SSA, cross-block data
flow, a bytecode verifier, and property/fuzz testing.

## Resume Bullets

- Built a Rust compiler pipeline from scratch — hand-written lexer and recovering
  recursive-descent parser, lexical resolver, static type checker, documented
  register IR, deterministic bytecode, and source-mapped diagnostics.
- Implemented constant folding and fixed-point dead-result elimination; on an
  81-function benchmark they folded 402 constants and removed 722 instructions,
  producing 336 bytecode instructions — reproduced identically across 32 runs.
- Designed a sandboxed register VM with checked arithmetic and configurable
  instruction/call/output limits; measured a median 128.8M instructions/s
  (range 19.8–153.0M over 32 runs) across 5.0M release-mode dispatches.
- Diagnosed and fixed a platform-specific determinism bug in the diagnostic
  renderer: the color backend's global switch probed for an attached console, so
  colored output silently degraded in a detached process and the snapshot suite
  passed or failed depending on how it was spawned.
